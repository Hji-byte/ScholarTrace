# Literature Review

How do research systems mitigate cold starts in serverless computing, and how do prewarming, snapshotting, and prediction-based approaches compare?

## Summary
Research systems mitigate serverless cold starts through three primary mechanisms: prewarming, snapshotting, and prediction-based scheduling [1, 2, 3]. Prewarming maintains warm containers to serve immediate requests but struggles with resource elasticity and unpredictable workloads [1, 5]. Snapshotting bypasses initialization by restoring function state from disk, though it historically suffers from high restore latencies and page fault overheads unless supported by OS-level co-design [1, 4]. Prediction-based approaches attempt to anticipate invocations to proactively allocate resources, but face significant challenges regarding forecasting accuracy and coordination with request admission [3, 5].

## Prewarming and Pool-Based Mechanisms
Basic prewarming mechanisms, such as those implemented in OpenWhisk, allocate only the container runtime rather than the function itself, making them suitable primarily for stateless workloads that lack long application initialization overhead [6]. A more structured pool-based approach to maintain warm containers in the Knative Serving platform achieved an 85% reduction in P99 response time for a single instance pool [6]. However, keeping sandboxes warm or relying on keep-alive policies fundamentally hurts resource elasticity and wastes resources because user request arrivals are difficult to predict [1, 3, 5]. Furthermore, pre-warming functions using checkpoint images or caches effectively bypasses initialization but increases memory usage, straining limited cache resources [5]. 

The theoretical foundations of serverless cold start mitigation differ significantly from traditional caching. While traditional caching leverages both temporal and spatial locality and allows shared access among users, serverless mitigation relies solely on temporal locality because function instances are mutually exclusive for security purposes [6]. Consequently, runtime-level optimizations like container reuse and sharing, which attempt to exploit spatial locality, raise severe deployment challenges due to security and isolation concerns [3].

## Snapshotting and Checkpointing Strategies
Snapshotting mitigates cold starts by capturing a function's complete state on disk after a full boot, allowing the orchestrator to rapidly load a new instance and bypass initialization steps without requiring major architectural changes [2, 4]. Different systems employ distinct isolation mechanisms to achieve this. The SEUSS method utilizes unikernels and defines coldest, warm, and hot execution paths, where the hot path restores a snapshot of a fully initialized User Container to bypass all startup steps [2]. In contrast, the Prebaking technique relies on standard operating systems and generates snapshots by executing the application offline, forcing initialization steps such as loading and compiling code and dependencies prior to actual deployment [2]. 

Experimental evaluations demonstrate that Prebaking outperforms SEUSS, initializing simple and complex functions 25% to 33% faster and processing the first request of complex functions 69% faster [2]. For a Markdown function, SEUSS increased first-request processing time by 9.6%, whereas Prebaking reduced it by 34% [2]. Despite these initialization benefits, executing a function from a snapshot results in execution times that are 95% higher on average compared to memory-resident execution due to frequent page faults when loading state from disk [4]. Additionally, snapshotting alone fails to reduce resource redundancy because multiple virtualization stacks must still be launched from a common snapshot [7]. 

Analysis shows that OS-level limitations, rather than storage speed, are the primary barrier to achieving ultra-fast, sub-millisecond restores from disk [1]. To address this, the Spice prototype engine utilizes OS co-design, including new kernel mechanisms for memory management to eliminate page fault overhead, successfully reducing cold restore latency to under 5ms [1].

## Prediction-Based Scheduling and Forecasting
Prediction-based approaches anticipate function invocations to preemptively mitigate cold starts. The IceBreaker system employs Fourier-based forecasting to estimate future invocations and leverages server heterogeneity by initially placing functions on low-end servers before migrating them to high-end servers as invocation likelihood increases [3]. Alternatively, a Prediction-Based Autoscaler (PBA) uses the SARIMA time series forecasting model to predict incoming request times and dynamically adjust container counts, subduing the effect of cold starts gracefully while consuming 18% fewer resources than the default Kubernetes Horizontal Pod Autoscaler [8]. 

Model Predictive Control (MPC) frameworks offer a more coordinated approach by jointly optimizing container prewarming and request dispatching based on forecasted future invocations [3]. An MPC-based proactive scheduling approach implemented on Apache OpenWhisk achieved up to 85% lower tail latency and a 34% reduction in resource usage compared to state-of-the-art baselines [3]. The MPC-based scheduler outperforms IceBreaker because it briefly queues and defers request dispatch to align with available warm containers, whereas IceBreaker immediately forwards requests and triggers cold starts when warm containers are unavailable [3]. 

However, prediction-based prewarming approaches, including those using machine learning or invocation pattern mining, often lead to resource inefficiency due to inaccurate predictions in dynamic production environments [5]. Reactive or predictive prewarming approaches frequently lack coordination with request admission, which causes delays under bursty workloads [3]. For instance, IceBreaker fails to coordinate prewarming completion with request dispatch, causing early requests to still incur full cold start latency [3].

## Limitations and Open Problems
The available evidence highlights distinct limitations across the three mitigation strategies. Prewarming and keep-alive policies inherently struggle with resource elasticity and waste resources due to the unpredictable nature of user request arrivals [1, 3, 5]. Traditional snapshot and restore approaches suffer from restore latencies that remain significantly higher than warm starts, which has historically prevented their widespread adoption [1]. While OS co-design like Spice addresses page fault overheads [1], general snapshotting still incurs a 95% average execution time penalty due to disk page faults [4] and fails to eliminate virtualization stack redundancy [7]. 

Prediction-based methods face a dual challenge: inaccurate forecasting in dynamic environments leads to resource inefficiency [5], and a lack of coordination between prewarming completion and request admission causes delays during bursty workloads [3]. Future research must address the integration of highly accurate forecasting with request shaping and admission control to fully realize proactive scheduling without incurring severe resource overheads.
