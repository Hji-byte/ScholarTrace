# Literature Review

Which datasets, benchmarks, and metrics are used to evaluate software supply-chain vulnerability and malicious-package detection methods?

## Summary
Evaluating software supply-chain vulnerability and malicious-package detection methods relies on a diverse set of datasets, benchmarks, and metrics [1, 2]. Existing data resources range from metadata and static collections to dynamic execution traces, each serving specific evaluation needs [1, 3]. Standard evaluation metrics, including precision, recall, F1 score, and false positive rate, are utilized to measure the effectiveness of detection tools in distinguishing malicious packages from benign ones, particularly those exhibiting risky characteristics [2, 4].

## Datasets and Benchmarks for Supply-Chain Evaluation
Existing software supply-chain datasets are categorized into metadata, static, hybrid, and dynamic types, where metadata datasets rely on non-execution-based features such as package names and version histories [1]. To construct ground-truth datasets, researchers manually curate malicious packages from vulnerability databases and security advisories; for instance, the Backstabber's Knife Collection covers JavaScript, Python, and Ruby ecosystems [3]. For vulnerability-specific evaluation, the PyVul dataset was automatically collected to address the lack of benchmarks that effectively map to Python packages, achieving a label accuracy of 93.1% and serving as a benchmark against datasets like SVEN, CVEFixes, and CrossVul [4].

To capture dynamic threats, the QUT-DV25 dataset comprises 14,271 PyPI packages (including 7,127 malicious ones) and captures 36 dynamic features, such as system calls, network activity, and installation traces, supporting the training of machine learning models using eBPF-collected behavioral data [1]. Furthermore, specific detection frameworks are evaluated against custom benchmarks. The OSCAR framework, for example, is evaluated on a benchmark of 500 malicious and 1,500 benign NPM and PyPI packages sourced from Snyk, OSV, and Socket Security, alongside a constructed Risk-Characteristic Benign Dataset, and is benchmarked against baseline tools including Bandit4Mal, AppInspector, OSSGadget, SAP, Amalfi, and Guarddog [2].

## Evaluation Metrics and Baseline Comparisons
The effectiveness of malicious package detection systems relies on evaluating performance metrics against comprehensive datasets containing both benign and malicious behaviors [1]. In practice, true positives, false positives, and false negatives are used to assess classification performance, whereas precision, recall, and F1 score are utilized to measure overall effectiveness [2]. Additionally, the false positive rate is specifically used to measure improvements over existing static detection tools when evaluated on risk-characteristic benign datasets [2]. Beyond dynamic and behavioral detection, rule-based static analysis methods like CodeQL, PySA, and Bandit are also utilized and evaluated for identifying vulnerabilities in Python packages [4]. 

As a baseline for dynamic analysis, the QUT-DV25 study provides an evaluation of four popular machine learning and two deep learning models on its proposed dataset [1]. In practical tool comparisons, OSCAR has achieved F1 scores of 0.95 in NPM and 0.91 in PyPI, while reducing false positive rates by 32.06% in NPM and 39.87% in PyPI on risk-characteristic benign datasets [2].

## Limitations and Open Problems
Despite the availability of various benchmarks, widely adopted metadata and static dataset benchmarks, such as the PyPI Malware Registry, Backstabber's Knife Collection, DataDog, and PyPIGuard, fail to execute packages during installation [1]. This limitation restricts their ability to detect dynamic threats like typosquatting, remote access activation, and install-time-specific payload generation [1]. Furthermore, existing curated datasets exhibit ecosystem biases; for example, the Backstabber's Knife Collection is highly biased towards npm and lacks malicious packages for Java and PHP [3]. Future research must address these gaps by expanding dynamic datasets to additional ecosystems, incorporating environment-sensitive attacks, and improving the mapping of vulnerability benchmarks to specific package execution contexts [1, 4].
