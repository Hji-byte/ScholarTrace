# Literature Review

Which datasets and evaluation protocols are used for machine-learning-based source-code vulnerability detection, and which forms of data leakage can inflate reported performance?

## Summary
This literature review examines the datasets, evaluation protocols, and data leakage issues prevalent in machine-learning-based source code vulnerability detection. Commonly used datasets, such as BigVul and Devign, are primarily code-based and sourced from open-source projects and vulnerability databases [1, 2, 3], though they often suffer from noisy labels and high duplication [1, 2]. Standard evaluation relies heavily on accuracy and F1 scores [1, 3, 4], despite the inappropriateness of accuracy for imbalanced data [1], prompting the introduction of more rigorous protocols like the Vulnerability Detection Score (VD-S) and chronological data splitting [1]. Furthermore, reported model performance is frequently inflated by specific forms of data leakage, namely "code copy" and "time travel" [1], alongside poor data quality, leading to significant performance drops in real-world scenarios [1, 2].

## Commonly Used Datasets and Data Sources
Machine learning models for source code vulnerability detection are frequently evaluated using datasets such as BigVul, CVEFixes, CodeXGLUE, DiverseVul, Devign, ReVeal, and D2A, which often consist of function-level C/C++ source code extracted from open-source projects [1, 3, 4]. Broadly, these datasets can be classified into Benchmark, Collected, and Hybrid sources, and are typically constructed from open-source software projects, public vulnerability databases, and bug repositories [2]. In primary studies, the majority of datasets are code-based, primarily utilizing source code, while repository-based datasets frequently rely on code changes and commits [2]. Specific examples include the Vuldeepecker dataset, which combines real-world samples from the National Vulnerability Database with synthetic samples from the Software Assurance Reference Dataset [3, 5], and the SATE IV Juliet Test Suite, which provides synthetic code examples augmented with natural code from Debian packages and GitHub repositories [5]. Additionally, Python-specific datasets often target GitHub repositories to detect vulnerabilities such as SQL injection [6]. 

Despite their widespread use, these datasets exhibit significant limitations. Most large vulnerability detection datasets rely on automatic labeling, which results in highly noisy labels; in some cases, nearly half of the vulnerable samples possess incorrect labels, compromising the trustworthiness of the models [1]. For instance, researchers have identified incorrect labels in the BigVul dataset [4]. Furthermore, inappropriate preprocessing or representation of source code data can lead to poor performance in deep learning-based vulnerability detection models [2].

## Evaluation Metrics and Protocols
The standard evaluation metrics for assessing source code vulnerability detection models are accuracy and the F1 score [1, 3, 4]. However, accuracy is widely considered an inappropriate metric for these tasks due to the typically imbalanced nature of vulnerability datasets [1]. To address class imbalance, the Matthews Correlation Coefficient (MCC) is often utilized [4], while benchmarks like CodeXGLUE continue to use accuracy as their primary metric [3]. 

To improve evaluation rigor and better reflect practical deployment, new protocols have been introduced. The Vulnerability Detection Score (VD-S) evaluates practical performance by measuring the false negative rate after tuning the detector to maintain the false positive rate below a fixed threshold [1]. Additionally, a pair-wise evaluation method has been proposed to assess a model's ability to distinguish between a vulnerable code sample and its benign counterpart [1]. To mitigate data leakage and prevent performance inflation, rigorous evaluation protocols recommend splitting samples chronologically to reflect the evolution of vulnerabilities and employing stringent de-duplication. For example, the PRIMEVUL dataset utilizes chronological temporal splits based on commit dates (80% training, 10% validation, 10% testing) to address high duplication rates [1].

## Data Leakage and Performance Inflation
Data leakage significantly inflates the reported performance of source code vulnerability detection models. Two specific types of leakage are prevalent: "code copy" and "time travel." Code copy leakage occurs when exact copies of vulnerable functions appear in both the training and evaluation sets; this inflates performance due to the high repetitiveness of code and the strong memorization capabilities of language models [1]. Time travel leakage occurs when code samples from the same commit are randomly separated into the training, validation, and test sets, unrealistically leaking information from the test time to the training time [1]. 

Performance inflation is further driven by high data duplication rates, with up to 18.9% of test samples leaked from the training set in some benchmarks, as well as the unrealistic distribution of vulnerable classes and the use of unbalanced or intentionally produced datasets [1, 2, 3]. Consequently, these benchmarks significantly overestimate model performance. The combination of data leakage, high duplication, and poor data quality—such as the incorrect labels identified in the BigVul dataset—leads to unreliable model performance. When evaluated in real-world scenarios, model performance can drop by more than 50 percent compared to standard benchmarks [1, 2, 4].

## Limitations and Open Problems
The available evidence highlights several critical limitations and open problems in the field. Existing vulnerability datasets suffer from poor data quality, low label accuracy due to reliance on automatic labeling, and high duplication rates, all of which lead to unreliable model performance in realistic scenarios [1, 2]. Current evaluation metrics, such as accuracy, often fail to capture the practical utility of models, necessitating the adoption of more rigorous protocols like the Vulnerability Detection Score (VD-S) and chronological data splitting [1]. Addressing these foundational data and evaluation flaws remains a primary open problem to ensure that code language models are genuinely effective for real-world vulnerability detection.
