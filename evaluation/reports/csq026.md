# Literature Review

What limitations have been reported for large-language-model agents on repository-level software engineering tasks, especially in localization, long-context reasoning, testing, and reproducibility?

## Summary
Large language model (LLM) agents face significant limitations in repository-level software engineering tasks, primarily driven by context window constraints [1, 2], complex cross-file reasoning requirements [7], and tool-usage inefficiencies [1, 3]. Fault localization is hindered by the inability to process entire repositories in a single pass [1] and a lack of advanced semantic retrieval mechanisms [3]. Automated testing and test-driven development are constrained by indirect call chains and a reliance on developer-written tests [3]. Furthermore, agent autonomy, collaboration, and resource awareness remain underdeveloped [5, 9], while evaluation methodologies and the nondeterministic nature of LLM generation pose substantial challenges to reproducibility [4, 8].

## Long-Context Reasoning and Fault Localization
Pretrained large language models cannot process entire software repositories in a single forward pass due to context window limitations [1]. Consequently, breaking a repository into smaller pieces for direct prompting falls short for identifying non-local bugs that require reasoning across interconnected code snippets spanning multiple files [2]. This limitation is particularly critical because 76% of the top 25 critical software weaknesses require global, path-sensitive reasoning across call graphs and control-flow graphs, which cannot be effectively identified through localized AST analysis [2]. Furthermore, limited context windows and hallucinations degrade the quality of bug reports during repository-level code auditing, while analyzing large-scale repositories incurs substantial time and token costs that hinder efficiency and scalability [2]. LLM capabilities generally wane at the repository scale due to the multifaceted challenges of processing extensive contexts and navigating intricate file interdependencies [4]. Agents exhibit persistent performance gaps on tasks requiring complex cross-file reasoning [7], global spatial reasoning, hardware-level engineering insight, or tightly coupled cross-file updates [7]. In large-scale C++ codebases, existing systems lack mechanisms for resolving identifier ambiguity and navigating deep syntactic structures, preventing reliable localization [8]. 

To manage these constraints, issue localization is utilized to reduce the search space for LLM agents [1]. However, existing repository-level agents lack semantic retrieval as an API beyond basic repository navigation, often requiring multiple attempts to locate the desired context [3]. Additionally, equipping repository-level LLM agents with excessive tools does not necessarily improve their code navigation and localization performance [1].

## Task Execution, Testing, and Agent Capabilities
Beyond localization, LLMs struggle with repository-scale code understanding, specifically failing to determine the correct arguments for calling routines and accurately configuring parameters when executing program files [4]. They also exhibit a capability bottleneck in generating bash scripts compared to Python code when executing repository-level tasks [4]. In the domain of automated testing, automating Test-Driven Development (TDD) at the repository level is challenging because tests reach target functions through long, indirect call chains and relevant context is scattered across the repository [3]. Strategically leveraging large test suites for specification enhancement to guide LLMs under computational budgets remains an open question [3]. Furthermore, current test-driven development frameworks are limited by their reliance on developer-written tests rather than enabling agents to co-evolve tests with implementations [3]. In specialized domains such as scientific repositories, LLM agents face distinct limitations arising from scientific correctness rather than standard code repair or file localization failures [7]. 

The design and training of LLM agents introduce further limitations. Mainstream agents typically acquire tool usage through few-shot prompting rather than pretraining, which is insufficient for learning complex multi-step tool-chaining behaviors [1]. Agent-based approaches are also limited by their strict requirement for high-quality, task-aligned training data to effectively navigate repositories and localize bugs [6]. Architectural choices impact autonomy; agents designed to operate in fixed phases, such as performing localization before repair, suffer from reduced autonomy in decision-making compared to more autonomous designs [5]. Despite improvements in unified software engineering agents, there remain existing gaps in their overall capabilities when handling diverse repository-level tasks [5]. In collaborative software engineering scenarios, existing LLM agents demonstrate consistently low collaboration willingness, indicating fundamental limitations in teamwork [9]. They also show a significant lack of resource awareness, as evidenced by minimal performance differences in resource-aware out-of-sync recoveries [9].

## Reproducibility and Evaluation Constraints
Reproducibility and evaluation methodologies present additional challenges. Benchmarks that rely on pre-built packages constrain the exploration of custom-built algorithms and potentially limit the reproducibility and customization of findings for subsequent researchers [4]. Similarly, evaluating repository-level tasks strictly based on README file descriptions may overlook potential applications or challenges that are not explicitly documented in the repository [4]. The nondeterminism of LLM generation poses a threat to the internal validity and reproducibility of findings in repository-level code resolution tasks [8]. Practical reproducibility issues are also evident, as demonstrated by researchers failing to reproduce the code for the OrcaLoca issue localization framework [1].

## Limitations and Open Problems
The literature highlights several open problems and limitations. Key challenges include enabling agents to co-evolve tests with implementations and strategically leveraging large test suites under computational budgets [3]. Improving semantic retrieval APIs and resolving identifier ambiguity in complex languages like C++ are necessary for better fault localization [3, 8]. Furthermore, enhancing agent autonomy, collaboration willingness, and resource awareness remains an open area of research [5, 9]. Finally, addressing the nondeterminism of LLM generation and improving the reproducibility of agent frameworks and benchmarks are critical for advancing repository-level software engineering [1, 4, 8].
