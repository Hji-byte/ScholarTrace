# Literature Review

How do execution-based, test-based, and model-based evaluation approaches for code generation compare?

## Summary
Evaluating code generation requires balancing functional correctness, computational efficiency, and annotation cost. Execution-based and test-based evaluation approaches rigorously assess functional correctness by running code against unit tests or matching desired outputs, providing a more reliable indicator of quality than surface-form metrics [1, 3, 6]. However, these methods are time-consuming and face high human annotation costs [1, 3]. To address these trade-offs, model-based evaluation approaches have emerged, utilizing pre-trained language models to either predict execution accuracy or automatically generate test cases [2, 6, 7]. These model-based methods substantially reduce computation time while maintaining strong correlations with ground-truth execution [2, 4], though challenges remain in evaluating non-functional code qualities and ensuring the sufficiency of test cases [3, 4].

## Methodological Differences and Evaluation Mechanisms
Execution-based and test-based evaluation methods verify functional correctness by checking whether generated code passes human-written unit tests or matches desired execution outputs [1, 3, 6]. These approaches rigorously assess code functionality, capture detailed errors, and allow for alternative correct solutions, unlike execution-free, surface-form metrics which only measure lexical or syntactic differences [1, 2, 3, 6]. While surface-form metrics may assign high scores to incorrect code due to lexical overlap and fail to account for functional correctness, they retain the potential to identify simple bug fixes [1, 3]. 

To scale test-based evaluation, frameworks like CodeBenchGen leverage large language models (LLMs) to automatically generate test cases and sandbox arbitrary code fragments into scalable benchmarks [1, 6]. Additionally, model-based tools using pre-trained language models can match or outperform traditionally built tools for test case and test oracle generation while requiring significantly less development effort [7]. Model-based evaluation metrics, such as CodeScore, take a different approach by learning to predict execution accuracy or pass ratios directly from the code [2, 4]. This neural approach reduces execution time by three orders of magnitude compared to traditional execution-based metrics while achieving strong correlation with ground-truth execution [2, 4].

## Correlation, Model Ranking, and Benchmark Impact
The choice of evaluation approach significantly impacts the ranking and selection of code generation models. Model rankings produced by execution-free metrics, including match-based and LLM-based metrics, do not precisely align with execution accuracy rankings and exhibit low correlation with functional correctness [1, 2]. These execution-free metrics show negligible variances between passed and failed samples, limiting their ability to discriminate code quality [1, 2]. In contrast, model-based metrics like CodeScore substantially outperform match-based and LLM-based metrics and maintain high correlation with execution accuracy [2, 4]. 

Empirical studies demonstrate that models achieving high surface-form evaluation scores do not necessarily perform well on execution metrics, particularly in data science code generation tasks, indicating that execution-based metrics are necessary to capture true code generation errors [3]. Furthermore, execution-based evaluation reveals that model proficiency is not uniform across domains; for instance, pass@1 can drop below 10% on libraries with complex functionalities such as matplotlib and tensorflow [1]. To address previous limitations where resources were restricted to closed-domain code, datasets like ODEX and ExeDS have extended execution-based evaluation to open-domain and data science code generation [1, 3]. 

The efficiency of test cases also plays a critical role in evaluation and generation. Using execution signals or injecting exemplar test cases during code generation significantly improves execution accuracy, enabling smaller models to perform comparably to larger ones [1, 2, 5]. However, computing execution-based metrics with too few test cases reduces correlation coefficients, highlighting the importance of sufficient test coverage [2, 4].

## Limitations and Open Problems
Despite their rigor, execution-based evaluation methods are more time-consuming to compute than surface-form metrics and are insufficient for evaluating non-functional code qualities like semantic relatedness and variable naming [1, 3]. There is also a fundamental trade-off between evaluation effectiveness and annotation efficiency due to the high human cost of creating comprehensive test cases [1, 3]. While model-based approaches and LLM-driven frameworks offer scalable alternatives for test generation and metric prediction, relying on automated or model-based judges may introduce noise if the underlying test cases are rare or low-quality [2, 4]. Future work must address the limitations of execution metrics in capturing non-functional qualities and further explore the reliability of LLM-as-a-judge paradigms compared to ground-truth execution.
